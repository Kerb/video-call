## Context

Приложение должно обеспечивать видеосвязь между 2+ пользователями через браузер с анонимным доступом по 6-значному коду комнаты. См. proposal.md для мотивации и specs для требований.

**Технические ограничения:**
- WebRTC требует HTTPS (кроме localhost)
- Для обхода NAT могут потребоваться STUN/TURN серверы
- Браузеры требуют разрешения пользователя на доступ к медиа-устройствам
- Signaling необходим для обмена SDP и ICE-кандидатами перед установкой P2P-соединения

## Goals / Non-Goals

**Goals:**
- Реализовать P2P-видеосвязь через WebRTC с использованием Socket.io для сигнализации
- Поддержка 2+ участников через mesh-архитектуру (каждый соединяется со всеми)
- Анонимный вход по 6-значному коду без регистрации
- Текстовый чат в реальном времени через Socket.io
- Демонстрация экрана через getDisplayMedia API
- Переподключение при разрыве соединения

**Non-Goals:**
- Регистрация пользователей и система аккаунтов
- Запись видеозвонков
- Мобильные нативные приложения (только мобильные браузеры)
- Приватные комнаты с паролем
- Интеграция с календарями

## Decisions

### 1. Архитектура: Фронтенд + Signaling-сервер

**Решение:** Статический фронтенд (Vanilla JS) + Node.js сервер с Socket.io для сигнализации.

**Обоснование:**
- Vanilla JS минимизирует зависимости и сложность сборки
- Socket.io предоставляет надёжный WebSocket с автоматическим переподключением
- Signaling-сервер Stateless — не хранит состояние комнат, только передаёт сообщения
- P2P-трафик идёт напрямую между клиентами, не через сервер

**Альтернативы:**
- React/Vue.js — избыточно для простого интерфейса, увеличивает размер бандла
- WebSockets напрямую — Socket.io даёт переподключение и фоллбэки из коробки
- Fullstack приложение — разделение упрощает деплой фронтенда на CDN

### 2. WebRTC топология: Mesh для малых групп

**Решение:** Каждый клиент устанавливает P2P-соединение со всеми остальными участниками (full mesh).

**Обоснование:**
- Для 2-5 участников mesh эффективен (n*(n-1)/2 соединений)
- Нет задержки на сервер-микшер (SFU/MCU)
- Проще реализовать без дополнительной инфраструктуры

**Альтернативы:**
- SFU (Selective Forwarding Unit) — лучше для 5+ участников, но требует медиа-сервер (mediasoup, Janus)
- MCU — избыточно, требует транскодирования на сервере

**Ограничение:** При 6+ участниках качество может ухудшиться из-за количества соединений и нагрузки на CPU/сеть.

### 3. Генерация кода комнаты: Base36

**Решение:** Код комнаты генерируется через `Math.random().toString(36).substring(2, 8).toUpperCase()`.

**Обоснование:**
- Base36 даёт 36^6 ≈ 2.2 млрд комбинаций
- Латинские буквы + цифры соответствуют требованиям
- Простая реализация без внешних зависимостей

**Альтернативы:**
- UUID — слишком длинный (32+ символа)
- crypto.randomUUID() — требует постобработки для сокращения

### 4. Хранение состояния комнаты: In-Memory на сервере

**Решение:** Сервер хранит активные комнаты в Map<code, Set<socketId>> в памяти.

**Обоснование:**
- Комнаты временные (очищаются через 60 мин после ухода всех)
- Не требует персистентности (БД)
- Быстрый доступ O(1)

**Альтернативы:**
- Redis — избыточно для MVP, добавляет зависимость
- База данных — не нужно, состояние эфемерное

### 5. STUN/TURN серверы

**Решение:** Использовать публичные STUN серверы Google для MVP. TURN не включать по умолчанию.

**Обоснование:**
- Публичные STUN бесплатны: `stun:stun.l.google.com:19302`
- ~80-90% соединений работают через STUN
- TURN требует инфраструктуры и затрат на трафик

**Альтернативы:**
- Развёртывание coturn — добавить в roadmap для production
- Cloud TURN сервисы (Twilio) — платно, добавить как опцию

### 6. Структура фронтенда: Vanilla JS с модулями

**Решение:** ES6-модули без сборщика:
- `main.js` — точка входа, инициализация
- `webrtc.js` — WebRTC логика (PeerConnection, медиа-потоки)
- `socket.js` — Socket.io клиент (сигнализация)
- `ui.js` — DOM манипуляции, обработчики событий
- `chat.js` — логика чата

**Обоснование:**
- Нет сборки — проще деплой и отладка
- ES6-модули работают во всех современных браузерах
- Чёткое разделение ответственности

### 7. Идентификация участников: Session ID

**Решение:** Каждый клиент генерирует `sessionId = crypto.randomUUID()` при входе.

**Обоснование:**
- Уникальный ID для идентификации в комнате
- Не требует регистрации
- Сохраняется в sessionStorage для переподключения

### 8. Максимальное число участников: 5

**Решение:** Ограничить максимальное число участников на уровне 5.

**Обоснование:**
- Mesh-топология эффективна до 5 участников (10 P2P-соединений)
- Предсказуемое качество связи
- Проще тестировать и документировать

**Реализация:** Сервер отклоняет `join-room`, если в комнате уже 5 участников. Клиент показывает сообщение "Комната переполнена".

### 9. Имена участников: ввод или генерация

**Решение:** Пользователь может ввести имя при входе. Если не ввёл — генерируется случайное двухсловное название (прилагательное + существительное), например "полосатый слон".

**Обоснование:**
- Баланс между персонализацией и простотой
- Генерация обеспечивает уникальность без регистрации
- Забавные имена улучшают UX

**Реализация:** 
- Список прилагательных (~50) и существительных (~50) на клиенте
- При создании/входе в комнату: поле ввода имени (опционально)
- Если поле пустое: `randomAdjective() + " " + randomNoun()`

### 10. UI: отзывчивый дизайн

**Решение:** Сразу делать отзывчивый UI для мобильных и десктопных браузеров.

**Обоснование:**
- Мобильные браузеры — часть требований
- CSS Grid/Flexbox упрощают адаптивную вёрстку
- Дешевле сделать сразу, чем переделывать

**Реализация:**
- Mobile-first подход
- Grid-сетка видео: 1 колонка на мобильном, 2-3 на десктопе
- Адаптивные кнопки управления (крупные для тача)
- Чат на отдельной панели или выдвижной на мобильных

## Risks / Trade-offs

| Риск | Последствие | Митигация |
|------|-------------|-----------|
| Нет TURN сервера | ~10-20% пользователей за симметричным NAT не соединятся | Добавить инструкцию для развёртывания coturn в production |
| In-memory состояние на сервере | Потеря комнат при рестарте сервера | Для MVP допустимо; для production добавить Redis |
| Vanilla JS без TypeScript | Нет типизации, выше риск ошибок | Добавить JSDoc комментарии, строгую ESLint конфигурацию |
| Публичные STUN серверы | Зависимость от Google, потенциальная нестабильность | Добавить альтернативные STUN в конфиг, рекомендовать свой coturn |
| Анонимный доступ | Возможность спама и злоупотреблений | Добавить rate limiting на создание комнат, модерацию по жалобам |
| Генерация имён | Возможны повторы или неуместные комбинации | Достаточно большой список слов (~50x50=2500 комбинаций), ручная проверка списка |

## Migration Plan

### Этап 1: Базовая функциональность
1. Настроить Socket.io сервер (signaling)
2. Реализовать создание/вход в комнату
3. Реализовать WebRTC PeerConnection (1-on-1)
4. Добавить передачу аудио/видео

### Этап 2: Расширения
1. Поддержка 3+ участников (mesh)
2. Текстовый чат
3. Демонстрация экрана
4. Управление устройствами

### Этап 3: Надёжность
1. Переподключение при разрыве
2. Обработка ошибок
3. STUN/TURN конфигурация

### Деплой
- Фронтенд: статический хостинг (Netlify, Vercel, GitHub Pages)
- Сервер: Node.js хостинг (Heroku, Railway, VPS)
- HTTPS обязателен (Let's Encrypt для VPS)

### Rollback
- Откат через git revert
- Сервер stateless — достаточно откатить код
- Фронтенд — откатить статику на хостинге
